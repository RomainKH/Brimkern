# A 0.1B model does not read your docs: 6/24

Everyone wants the ~60 MB in-browser support widget. We measured what that actually costs.

Brimkern's embeddable widget does document Q&A in the browser (WebGPU, no server): the page gives
it fact sheets, it answers from them, and it must **refuse** anything outside them. Its default
model weighs 149 MB. The obvious question, asked for ten days: can RWKV-7 G1 0.1B — Apache-2.0,
~105 MB floor as a `.brik` — take its place?

We wired the RWKV-7 dispatch into the SDK (70 lines) precisely so this would be a measurement
instead of an opinion. `sdk-rag.mjs`, two full rounds, English and French, same bench the default
model passes:

**6/24.**

The failure pattern is the interesting part. The model doesn't answer *wrong* — it serves the
canonical refusal **while the correct fact sheet is selected and sitting in its context** (round 2,
English: 4 refusals on the 4 sheet-backed questions). And when it does read, it copies the entire
sheet — including the one amount the instructions forbid it to reveal. What survives: greetings,
and refusals when there genuinely is no sheet. Those are its known strengths — conversation,
constrained classification — not the widget's job. Reading a fact sheet is simply above what this
0.1B can do, in any file format.

For calibration, same bench, same harness:

- LFM2.5-230M (149 MB, LFM Open License v1.0) → **12/12**
- RWKV-7 G1a 0.4B (304 MB, Apache-2.0) → **10/12** — and both misses are the *same* case, reading
  one row of a table (26.0/26.5 cm instead of 27.0)

So the licensing trade-off is now a number: going Apache costs 2× the download and one table-row
read. And the "small model = widget" shortcut closes with a bench, not a mood: below some capability
floor, the model doesn't degrade gracefully — it stops doing the *task* while still sounding fine.
